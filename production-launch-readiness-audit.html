Do not deploy until Wave 1 and Wave 2 are closed. The build is green and the test suite passes, which is exactly why these are easy to miss: none of them announce themselves at build time. The paywall cannot hold, account deletion does not delete, forgotten passwords are unrecoverable, and the checkout screen shows a price Stripe is never asked to charge.

Start with P1. It is a decision, not code, and it changes how much of the rest is worth building.

Before you start

Get a working localhost first - verified from a clean clone of this branch.

# one variable is genuinely required; without it /api/auth/session returns 500
node -e "console.log('AUTH_SECRET=' + require('crypto').randomBytes(32).toString('base64'))" > .env.local
npm install --no-audit --no-fund
npm run dev        # http://localhost:3001

With only that set, the app runs on a JSON file store at .data/ with canned AI responses - no Postgres, Gemini, Stripe or Resend keys needed. Add DATABASE_URL to switch to Postgres (apply database/schema.sql first). GET /api/health reports which integrations are live. Full setup notes are in HANDOVER.md; the diagnostic report this worklist derives from is production-readiness-audit-2026-10-26.html.

Local gotcha: if the dev server starts panicking with Failed to write app endpoint ... Next.js package not found and the page appears to shake, the Turbopack cache is stale. Stop the server, rm -rf .next, restart. Switching branches triggers it.

P1DecisionProduct + eng

Decide the paywall model before writing any paywall code

The defect

Premium is a localStorage flag. Editing resume-co:paywall in devtools, or calling usePaywall.setState({premium:true}) in the console, unlocks everything. The server reconciliation only corrects that flag when the entitlement API answers source === "server", and it writes back into the same client store.

There is no server step to gate: all seven download entry points funnel into exportElementToPdf, which renders the PDF in the browser. No server-side check can rescue the current architecture - the file never passes through your infrastructure.

src/features/cover-letter/lib/paywall.ts · src/services/storage/{pdf-export,download-pdf}.ts
Do this
  1. Pick one: (a) server-rendered downloads - a route that authenticates, checks entitlement, renders the PDF server-side and streams it; or (b) accept the free tier - treat downloads as free and monetise something that genuinely requires your server (AI tailoring, job matching, stored documents).
  2. Option (a) is the real fix and the larger job: it means moving rendering off html2canvas-pro in the browser to a server renderer, and the output must match the current visual result.
  3. Option (b) is honest and cheap, but it is a pricing change - it needs the business to agree.
  4. Write the decision down in the PR description. Everything in P2 follows from it.
Done when
  • The chosen model is recorded and agreed, with the free tier defined explicitly.

P3CriticalPrivacy / GDPR

Make account deletion actually delete

The defect

pgDeleteUser runs one statement - delete from users - and its comment claims documents go via ON DELETE CASCADE. That cascade does not exist: schema.sql explicitly drops the foreign key so OAuth accounts can own documents.

Surviving deletion: documents (resumes - legal name, address, phone, employment history), saved_jobs, dismissed_jobs, tailoring_sessions, subscriptions. A Google-only account has no users row at all, so for those users the delete is a complete no-op while the UI reports success. The file store has the same hole: fileDeleteUser rewrites users.json and never touches documents.json.

Your published privacy policy says: “We keep your account and content until you delete them.”

src/services/database/users.ts:99 (file) · :185 (postgres) · database/schema.sql
Do this
  1. Rewrite pgDeleteUser to clear all six tables in one transaction keyed on the normalised email, never conditional on a users row existing. postgres@3.4.9 gives you sql.begin - confirmed available.
  2. Fix fileDeleteUser to match: strip the email from .data/documents.json as well as users.json.
  3. Decide what happens to a live subscription row. Cancellation already happens first in DELETE /api/account; keep a billing record only if you have a stated legal basis, and say so in the policy.
  4. Correct the misleading comment - it is what hid this.
// shape, not finished code
await sql.begin(async (tx) => {

  await tx`delete from tailoring_sessions where email = ${e}`;
  await tx`delete from subscriptions      where email = ${e}`;

Done when
  • A test seeds rows in all six tables, deletes the account, and asserts zero rows remain.
  • The same test passes for an OAuth-style account that has no users row.
  • The same test passes against the file store backend.

P4CriticalBilling disclosure

Make the displayed price the charged price

The defect

The trial plan shows priceLabel: "$1.95" and summaryAmount: "$1.95". The Stripe payload for the same plan is unitAmount: 2995 with trial_period_days: 7. The customer is charged $0.00 today and $29.95 in seven days. The figure $1.95 is never sent to Stripe.

This invites chargebacks, breaches consumer-disclosure rules in the EU, UK and several US states, and is a common trigger for Stripe account review and ad disapproval.

src/services/payments/plans.ts - PLANS.trial
Do this
  1. Decide the actual offer: a genuinely paid $1.95 trial (add a one-off $1.95 line item and drop the free trial days), or a free 7-day trial (relabel to “$0.00 today, then $29.95/month”).
  2. Derive every displayed figure from the same plan object the Stripe call uses. The bug exists because the labels are hand-written strings sitting next to the real amounts.
  3. Check the annual plan too while you are in there - confirm $119.40 matches unitAmount: 11940.
Done when
  • A test-mode checkout charges exactly what the summary says, for both plans.
  • No price string in the codebase is written independently of the Stripe amount.
P5CriticalAuth

Password reset, email verification, and the linking hole

The defect

No forgot-password route, page or token flow exists anywhere in src, and no email verification. A user who forgets their password is permanently locked out of their resumes.

Worse in combination: Google sign-in sets allowDangerousEmailAccountLinking: true while credential signup never verifies the address. An attacker registers a password account for victim@gmail.com; when the victim later signs in with Google the accounts link, and the attacker's password now opens the victim's account.

src/features/authentication/auth.ts · src/services/email/email.ts (only welcome + receipt exist)
Do this
  1. Set allowDangerousEmailAccountLinking: false now. This is a one-line change and closes the takeover path immediately.
  2. Add email verification on credential signup - single-use, expiring token.
  3. Add the reset flow: request, single-use expiring token, set-new-password. Resend is already wired; follow sendWelcomeEmail for the sending pattern.
  4. Re-enable account linking only once verification is enforced on both sides.
  5. While you are in the email service, the four missing lifecycle emails belong here too: payment failed, trial ending, subscription cancelled, deletion confirmation.
Done when
  • A real reset email arrives in a real inbox and the new password works.
  • Reset tokens are single-use and expire; a consumed token is rejected.
  • An unverified credential account cannot be linked to a Google sign-in.
P6CriticalDatabase

Introduce a migration ledger before any schema change ships

The defect

database/migrations/, policies/, functions/ and seed/ are all empty. The schema is one 105-line file applied by hand, and it already carries in-place drift repairs (drop constraint if exists) for databases created by earlier runs. There is no way to know what a production database contains, no rollback, and no CI check that code matches schema.

database/schema.sql · scripts/db-setup.mjs
Do this
  1. Freeze today's schema as database/migrations/0001_init.sql.
  2. Add a schema_migrations ledger table and make the runner idempotent - applied migrations are recorded and skipped.
  3. Apply to a fresh staging database and diff the result against schema.sql; they must match exactly.
  4. Add a CI job that applies migrations to an empty database, so drift fails the build rather than production.
  5. Every later task that touches the schema (P3's deletes, P8's ledger) ships as a numbered migration from here on.
Done when
  • A fresh database reaches the current schema from migrations alone.
  • Running the migration runner twice is a no-op the second time.
  • CI fails if a schema change lands without a migration.

P7HighPayments

Require a session at checkout and stop keying entitlement on a typed email

The defect

auth() is read but never required, so client_reference_id and the subscription metadata are omitted for anonymous buyers. The webhook then falls back to customer_details.email - the address the payer typed into Stripe's form - and grants premium to it. A mistyped address means the payer gets nothing with no link to any account; someone else's address grants premium to that account.

src/app/api/checkout/session/route.ts · src/app/api/stripe/webhook/route.ts
Do this
  1. Return 401 from the checkout route when there is no session.
  2. In the webhook, accept only client_reference_id and subscription metadata that your own server set. Drop the customer_details.email fallback.
  3. Longer term, key subscriptions on a stable user id rather than email, which is mutable. That is a migration (P6) plus a backfill.
  4. Add a rate limit to the checkout route - it currently has none, so session creation can be spammed.
Done when
  • An anonymous POST to the checkout route is refused.
  • Entitlement cannot be granted to an address the server did not supply.
P8HighPaymentsafter P6

Webhook idempotency and event ordering

The defect

Signature verification is correct - raw body, async verify, Node runtime, 500-on-error so Stripe retries. Two gaps remain. No event.id is recorded, so at-least-once delivery can send a duplicate receipt email. And entitlement writes stamp Date.now() rather than the event's own timestamp, so a subscription.updated arriving after subscription.deleted can silently restore cancelled access.

src/app/api/stripe/webhook/route.ts - const now = Date.now()
Do this
  1. Add a processed_events table (migration, per P6). Insert event.id and return early on conflict.
  2. Use event.created as the write timestamp instead of Date.now().
  3. Refuse any entitlement write whose event timestamp is older than the stored updated_at.
Done when
  • Replaying the same event twice produces one receipt email and one write.
  • An out-of-order update after a cancellation does not restore access.

P14HighData lossfound by QA handbook

Two tabs editing one document silently destroy each other's work

The defect

Document saves are an unconditional, whole-blob, last-write-wins overwrite. The upsert ends with on conflict (email, type, id) do update set data = excluded.data and no updated_at guard.

Open one resume in two tabs. Change the title in the first and the summary in the second. Both tabs hold a full snapshot, so whichever saves last replaces the entire document and discards the other edit with no warning. This is not a merge conflict, it is a total replacement. The same gap means a slow or retried request can overwrite a newer save with stale data. With autosave running, neither tab needs an explicit Save for this to happen.

src/services/database/documents.ts:198-202 - pgUpsertDocument, on conflict do update
Do this
  1. Guard the write: add where excluded.updated_at > documents.updated_at to the conflict clause so a stale save cannot land.
  2. Return a distinct status when a write is refused, and have the client tell the user their copy is behind instead of failing silently.
  3. Apply the same guard to the file-store backend, which has the identical whole-blob behaviour.
  4. Decide the product answer for a genuine two-tab conflict: refuse and reload, or merge at section level. Refusing is acceptable; silently discarding is not.
Done when
  • Two tabs editing different fields of one document no longer lose either edit.
  • A save carrying an older updated_at than the stored row is rejected.
  • The user is told when their save was refused.
Verify 
# the QA handbook's own test, section 14.1
# open the same resume in two tabs, edit a different field in each,
# save both, reload both - neither edit may disappear
P9HighAbuse / cost

The rate-limit identity is attacker-supplied

The defect

clientIp() returns the first entry of X-Forwarded-For, which the caller controls. Rotating that header per request defeats every IP-keyed limit. The AI endpoint accepts anonymous requests and is keyed on exactly this value, so your Gemini spend is uncapped by anyone willing to send a header.

src/permissions/rate-limit.ts:155
Do this
  1. Trust only the platform-provided client address - on Vercel the last hop, not the first entry a client can prepend.
  2. Require a session for /api/ai, or give anonymous callers a much smaller, separately-keyed budget.
  3. Treat Upstash as required in production. Without UPSTASH_REDIS_REST_URL/_TOKEN every limiter falls back to a per-instance Map, which on serverless makes both the login brake and the AI quota close to meaningless. GET /api/health already exposes sharedRateLimit - alert on it being false.
  4. Same fix protects /api/jobs (Adzuna quota) and /api/register (signup spam).
Done when
  • Rotating X-Forwarded-For no longer raises the effective quota.
  • Production refuses to run, or alerts loudly, with in-memory rate limiting.
P10HighLegal

Remove the LinkedIn scraping endpoint from the launch build

The defect

POST /api/linkedin fetches a LinkedIn profile page server-side and returns its text. No session, no rate limit - anyone on the internet can use the deployment as a scraping proxy, from your IP and under your platform account. Server-side scraping of profile pages also conflicts with LinkedIn's terms of service. The URL regex is anchored to linkedin.com/in/, so SSRF is contained; the abuse and legal exposure are not.

src/app/api/linkedin/route.ts
Do this
  1. Delete the route from the launch build. Project notes already record this feature as held pending a real LinkedIn API key - the endpoint should be held with it.
  2. If it must stay for internal testing, require a session and a rate limit, and keep it out of production builds.
Done when
  • The route returns 404 in a production build.
P11MediumData

Cap the document blob

The defect

PUT /api/documents stores an arbitrary record.data value as jsonb with no size limit, and there is no document-count cap outside resumes. One account can fill the database. Authorization itself is sound - every handler scopes by session email, and four isolation tests cover it.

src/app/api/documents/route.ts
Do this
  1. Validate the body with Zod, as /api/ai already does, including a maximum serialised size.
  2. Apply a per-account cap to cover letters, resignation letters and interview-prep sheets, not only resumes.
Done when
  • An oversized document is rejected with 413, and the caps have tests.

Does fixing this list make it launch-ready?

NO

Closing every task on this page clears the known blockers. It does not by itself make the product safe to launch. Treat this list as necessary, not sufficient. Three things stand between a completed worklist and a defensible go-live decision.

1. Sixteen requirements were never assessable

Everything marked BLOCKED in the inventory needs access that nobody has used yet: production environment variables and domains, the live database schema and its backups, Stripe dashboard configuration including whether it is in live or test mode, the Resend sending domain's SPF, DKIM and DMARC records, and repository branch protection. None of these can be inferred from code. Each one is capable of blocking a launch on its own - a webhook pointed at the wrong URL, or a sending domain with no DMARC record, will not announce itself.

2. Nothing here has been verified in a running browser

This audit is a source review plus executed build gates. No user journey has been run end to end, no page has been opened at a phone width, no accessibility tool has been pointed at the UI, and no load has been applied. A fix that typechecks and builds is not a fix that works. That is exactly what P13 exists for, and why it is the last task rather than an optional one.

3. A static review only finds what it can see

P14 on this page is the proof. The concurrent-save data-loss bug was not found by reading the code looking for bugs - it surfaced because an existing QA handbook asked a question this audit had not thought to ask. One prompt from one document produced one real defect. There is no reason to believe that was the last one. Expect the end-to-end tests, the staging pass and the first real users to each surface things this list does not contain.

What a defensible go-live actually requires

In order, after this worklist is closed:

  • Check the sixteen blocked items with real access, and record what was found rather than assuming it is fine.
  • Run the journeys - signup, login, build and download, checkout, entitlement revocation, deletion - against a staging deployment with its own database and Stripe test keys.
  • Prove the destructive paths: restore a backup, revoke a subscription, delete an account, and confirm each did what it claimed.
  • Pass a visual, responsive and accessibility pass at real viewports.
  • Settle the business decisions that are not engineering: the pricing model behind P1 and P4, the refund policy, tax handling, and processor disclosure.
  • Verify the live site after deploying, not before. A green deploy is not a verified product.

The honest summary: this worklist takes the project from unsafe to launch to ready to be verified. The verification is the part that earns a go-live, and it has not started.

Rules that keep it conflict-free

  • One step, one branch, one PR. Steps are sized so each is reviewable alone. The two paired steps (7 and 9) are single PRs precisely because splitting them would mean touching the same file twice.
  • Merge and rebase before starting the next step. The order assumes each step lands before the next begins. Two steps open at once reintroduces exactly the conflicts this ordering removes.
  • Never run step 3 in parallel with anything. It is the only step that rewrites files across the whole tree.
  • Run the four gates before every merge: npx tsc --noEmit, npm run test:run, npm run build, npm run lint. After step 3 all four should be green, and any later red is caused by the branch in front of you.
  • Tag after step 12. That is the first point where a deployable candidate exists. Deploy from a tag, never from a working tree.
  • If a second person is available, give them R1-R7 from step 4 onward. That track touches no file in steps 5 to 13.

After step 13, return to the previous section. The worklist is then closed, which means the product is ready to be verified - the sixteen blocked items checked with real access, the journeys run against staging, and the live site confirmed after deploy. That verification is what earns the go-live, and it is not part of this list.
