NO-GO

This application must not be launched in its current state. The engineering foundation is genuinely strong — clean typecheck, 113 passing tests, a correct Stripe webhook, parameterised SQL, real security headers and disciplined per-account data scoping. The blockers are not sloppiness; they are five load-bearing gaps that each defeat a core business or legal guarantee.

The paywall cannot hold, account deletion does not delete, a user who forgets their password is locked out forever, the checkout screen shows a price Stripe is never asked to charge, and there is no migration path to a production database. Five critical and eight high findings follow, each with its evidence and the smallest safe fix.

Critical — launch blockers

Each of these breaks a promise the product makes to its users, its payers, or the law. None can be deferred past launch.

CriticalStatic C1 · Payments / entitlement

The paywall is client-side only — every paid feature is free

Premium state lives in a Zustand store persisted to localStorage under the key resume-co:paywall. Editing that value, or calling usePaywall.setState({premium:true}) from the browser console, unlocks every gated action. The server reconciliation only corrects the flag when the entitlement API answers source === "server", and even then it writes into that same client store.

Compounding this: PDF export runs entirely in the browser via jspdf and html2canvas-pro. There is no server step in the download path to gate, so no server-side check can rescue it. The monetisation model is currently unenforceable.

src/features/cover-letter/lib/paywall.ts — persist({ name:"resume-co:paywall", partialize: s => ({ premium: s.premium }) })
unlock() → set({ premium:true }) — called on checkout return, never re-validated
src/services/storage/pdf-export.ts, download-pdf.ts — client-side render, no API call
Smallest safe fixMove the gated download to a server route that calls isPremium(session.user.email) before returning the file, and treat the client flag as presentation only. Until that route exists, the free tier is in practice whatever the app can do — so the alternative is to redefine the free tier as what you accept giving away.
CriticalStatic C2 · Privacy / GDPR

“Delete my account” leaves every piece of personal data behind

pgDeleteUser runs exactly one statement — delete from users — and its comment states that documents are removed “by the ON DELETE CASCADE on documents.email”. That cascade does not exist: schema.sql deliberately drops the foreign key so that OAuth accounts can own documents. Nothing cascades.

What survives deletion indefinitely: documents (full resumes — legal name, address, phone number, employment history), saved_jobs, dismissed_jobs, tailoring_sessions and subscriptions. Worse, a Google-only account has no users row at all, so for those users the delete is a complete no-op while the UI reports success. Your published privacy policy states “We keep your account and content until you delete them.”

src/services/database/users.ts:185 — pgDeleteUser(): delete from users where email = $1
database/schema.sql — alter table documents drop constraint if exists documents_email_fkey
src/app/(public)/privacy/page.tsx — "We keep your account and content until you delete them."
Smallest safe fixDelete from all six tables in one transaction keyed on the normalised email, independent of whether a users row exists. Add a security test that seeds rows in every table, deletes the account, and asserts zero rows remain.
CriticalStatic C3 · Authentication

No password reset, no email verification, and dangerous account linking enabled

There is no forgot-password route, page, or token flow anywhere in src, and no email verification. A user who forgets their password is permanently locked out of their resumes with no self-service recovery — on a paid product, that is a support and refund problem from day one.

The combination is also an account-takeover path. Google sign-in sets allowDangerousEmailAccountLinking: true while credential signup never verifies the address. An attacker can register a password account for victim@gmail.com; when the victim later signs in with Google the accounts link, and the attacker's password now opens the victim's account.

grep -rliE "forgot.?password|reset.?password|verif(y|ication).?(email|token)" src → no matches
src/features/authentication/auth.ts — Google({ allowDangerousEmailAccountLinking: true })
src/services/email/email.ts — only sendWelcomeEmail + sendReceiptEmail exist
Smallest safe fixShip a token-based reset flow (Resend is already wired) and verify the email address on credential signup. Until verification exists, set allowDangerousEmailAccountLinking: false.
CriticalStatic C4 · Billing disclosure

Checkout shows “$1.95 due” but Stripe is never asked to charge $1.95

The trial plan advertises priceLabel: "$1.95" and summaryAmount: "$1.95" on the payment and checkout pages. The Stripe payload for that same plan is unitAmount: 2995 with trial_period_days: 7. The customer is therefore charged $0.00 today and $29.95 in seven days. The figure $1.95 appears nowhere in the Stripe request.

A displayed price that does not match the amount charged invites chargebacks and breaches consumer-disclosure rules in the EU, the UK and several US states. It is also a common trigger for Stripe account review and Google Ads disapproval.

src/services/payments/plans.ts — trial: { priceLabel:"$1.95", summaryAmount:"$1.95",
  stripe:{ unitAmount:2995, interval:"month", trialDays:7 } }
Smallest safe fixDecide which product you are actually selling: a genuinely paid $1.95 trial (add a one-off $1.95 line item and drop the free trial days) or a free 7-day trial (change every label to “$0.00 today, then $29.95/month”). Either way, derive the summary from the same plan object the Stripe call uses instead of hand-writing it.
CriticalStatic C5 · Database operations

No migration path to production — schema changes are a manual paste

database/migrations/, policies/, functions/ and seed/ are all empty. The entire schema is a single 105-line schema.sql applied by hand, and it already contains evidence of drift being patched in place: drop constraint if exists blocks that repair databases created by earlier runs.

With no versioned, forward-only migrations there is no way to know what a production database actually contains, no rollback, and no CI check that the code matches the schema. The first schema change after launch would be an unrehearsed manual edit against live user data.

ls database/migrations database/policies database/functions database/seed → all empty
database/schema.sql:5 — "Apply once: node scripts/db-setup.mjs (or paste into the Neon SQL console)"
database/schema.sql:97-105 — in-place constraint repair for pre-existing databases
Smallest safe fixFreeze the current schema as migrations/0001_init.sql, add a schema_migrations ledger table, and make the runner idempotent. Apply it to a fresh staging database and diff the result against schema.sql.

High — fix before real users arrive

HighStatic H1 · Abuse / cost

Every IP-based rate limit is bypassable with one header

clientIp() returns the first entry of X-Forwarded-For, which the caller supplies. Rotating that header per request defeats the limit entirely. The AI endpoint accepts anonymous requests and is keyed on exactly this value.

src/permissions/rate-limit.ts:155 — const xff = req.headers.get("x-forwarded-for"); if (xff) return xff.split(",")[0]
Affects /api/ai (Gemini spend, 300/day default), /api/jobs (Adzuna quota), /api/register (signup spam)
Smallest safe fixTrust only the platform-provided client address (on Vercel, the last hop rather than the first), and require a session for the AI endpoint — or give anonymous callers a much smaller, separately-keyed budget.
HighStatic H2 · Payments

Checkout works while signed out, and entitlement is keyed on a payer-typed email

auth() is read but never required, so client_reference_id and the subscription metadata are simply omitted for anonymous buyers. The webhook then falls back to customer_details.email — the address the payer typed into Stripe's own form — and grants premium to it.

A payer who mistypes their email pays and receives nothing, with no record linking the subscription to any account. A payer who types someone else's address grants premium to that account instead. Entitlement is keyed on a mutable identifier rather than a user id.

src/app/api/checkout/session/route.ts — const email = session?.user?.email ?? undefined
src/app/api/stripe/webhook/route.ts — email = s.client_reference_id || s.customer_details?.email || s.customer_email
Smallest safe fixReturn 401 from the checkout route when there is no session, and have the webhook accept only the client_reference_id and subscription metadata your own server set.
HighStatic H3 · Payments

The webhook has no idempotency ledger and ignores event ordering

Signature verification and retry semantics are correct, but no event.id is recorded, so Stripe's at-least-once delivery can send a duplicate receipt email. Entitlement writes stamp Date.now() rather than the event's own timestamp, so a customer.subscription.updated event that arrives after customer.subscription.deleted can silently restore cancelled access.

src/app/api/stripe/webhook/route.ts — const now = Date.now(); … setEntitlementByCustomer(customerId, sub.status, end, now)
No processed_events table; no comparison against the stored updated_at
Smallest safe fixInsert event.id into a processed_events table and return early on conflict; use event.created as the write timestamp and refuse writes older than the stored one.

HighStatic H5 · Legal / third party

An unauthenticated LinkedIn scraping endpoint is live in the app

POST /api/linkedin fetches a LinkedIn profile page server-side and returns its text. It requires no session and has no rate limit, so anyone on the internet can use your deployment as a scraping proxy — from your IP, under your platform account. Server-side scraping of profile pages also conflicts with LinkedIn's terms of service.

src/app/api/linkedin/route.ts — export async function POST: no auth(), no limit()
The URL is constrained by PROFILE_RE (anchored, linkedin.com/in/ only) — SSRF is contained; abuse is not
Smallest safe fixRemove the route from the launch build. The project notes already record this feature as held pending a real LinkedIn API key — the endpoint should be held along with it.
HighBlocked H6 · Infrastructure

Rate limiting silently degrades to per-instance memory

Without UPSTASH_REDIS_REST_URL and UPSTASH_REDIS_REST_TOKEN every limiter falls back to an in-process Map. On serverless each invocation may get a fresh instance, which makes the login brute-force brake and the AI daily quota close to meaningless.

Whether this actually bites depends on production environment variables, which I cannot see. Recorded as BLOCKED, not PASS.

src/permissions/rate-limit.ts:30 — const buckets = new Map<string, Bucket>()
isSharedRateLimit() is already exposed by /api/health — assert it from a monitor
Smallest safe fixTreat Upstash as required in production: fail the deploy, or at minimum alert, when /api/health reports sharedRateLimit: false.

What is already right

Recorded so that the plan does not disturb it. Static inspection unless noted.

  • Stripe webhook construction is correct — the raw body is read before any parsing, the signature is verified asynchronously, runtime = "nodejs" is pinned, handler errors return 500 so Stripe retries, and the receipt email is wrapped locally so an email failure can never fail the event.
  • SQL is parameterised throughout via postgres.js tagged templates. I found no string-concatenated query anywhere.
  • Per-account data scoping is consistent — documents, saved jobs, dismissed jobs and tailoring sessions all key on the session email, and four isolation tests assert it.
  • The AI endpoint is well defended — Zod validation at the trust boundary, an upload MIME allowlist, a decoded-size cap, and both per-minute and per-day quotas. Only the identity it keys on is weak (H1).
  • Account deletion cancels Stripe subscriptions first and refuses to delete if that fails, returning a distinct 502 — exactly the right ordering. It is the deletion itself that is incomplete (C2).
  • Login has a real brute-force brake, keyed on email, counting only failures and resetting on success.
  • Security headers are present — nosniff, DENY framing, strict-origin referrer, a Permissions-Policy, and two-year HSTS with preload.
  • robots.txt and sitemap.xml are correct — every per-account surface is disallowed and only the four public routes are listed.
  • Secret hygiene is clean (executed) — .env* is ignored and git ls-files returns no env file. No secret value was read or displayed during this audit.
  • Sentry and PostHog are wired through instrumentation.ts and instrumentation-client.ts, and /api/health is a well-designed liveness probe.

Implementation plan

Ordered so that each step is verifiable before the next begins. Steps 1–4 are the minimum to move the verdict off NO-GO. Nothing here starts without your approval, and every Stage 3 change comes to you as a reviewable diff.

Stop the bleeding in billing and privacy

C2 (complete the deletion), C4 (make the displayed price the charged price), H2 (require a session at checkout), H3 (event ledger plus event timestamps).

Gate: a security test proving zero rows survive deletion, and a test-mode checkout whose charged amount matches the on-screen summary.

Decide and enforce the paywall

C1. This is a product decision before it is a code change: either the download moves server-side behind an entitlement check, or the free tier is redefined as what you accept giving away. I will bring you both options rather than choose for you.

Gate: with localStorage hand-edited to premium, a gated download still fails.

Close the account-recovery hole

C3. A token-based password reset over Resend, email verification on credential signup, and allowDangerousEmailAccountLinking switched off until verification ships.

Gate: a real reset email delivered to a real inbox, end to end.

Make the release process real

H8 (commit and PR the UI work), H4 (ESLint ignores plus the 62 real errors in src), C5 (freeze 0001_init.sql and add a migration ledger).

Gate: CI green on a PR into main, and migrations applied cleanly to a fresh staging database.

Harden the abuse surface

H1 (platform-trusted client IP, session required for AI), H5 (remove the LinkedIn route), H6 (require Upstash in production), M2 (cap the document blob).

Gate: header rotation no longer defeats the AI quota.

Prove the journeys

H7. Playwright specs for signup, login, build-and-download, checkout, entitlement revocation and account deletion, wired into CI.

Gate: six specs green in CI against the dev server.

Legal, consent and customer comms

M3 (a consent gate before PostHog and Sentry), M4 (rewrite the privacy policy to match reality, naming every processor), M5 (the four missing lifecycle emails, plus EMAIL_FROM in the env examples).

Gate: no analytics request fires before consent is given.

Stage 5 — staging, then operations

Stand up a staging deployment with its own database and Stripe test keys, verify SPF, DKIM and DMARC on the sending domain, document and rehearse a restore (M9), then set alerts on the health probe and write the rollback runbook (1P).

Gate: a restore actually performed, and a Go/No-Go re-run against Stage 6.
